# ESP32-P4 USB-Serial/JTAG TX FIFO store fault

ESP32-P4 v3.2 (ROM `esp32p4-eco7-20260109`) takes a store-access fault on a write to the USB-Serial/JTAG TX FIFO. The host CDC port is open. The same store is what IDF 6.1 uses: `USB_SERIAL_JTAG.ep1.val = byte`.

## This run

IDF v6.1, project `p4_usj_fifo_split`, ELF SHA256 `26145c56f`, chip rev v3.2 (`esp_chip_info` printed 302). `idf.py build flash monitor` is attached to the USB Serial/JTAG port. That session contains the build, the flash, and the monitor. The monitor prints, then it stops. UART0 (GPIO 37/38) is the console. The panic register dump is only there.

The log reached `lines 3900 last index 49`, then:

| Field | Value |
|---|---|
| Core | 0 |
| MCAUSE | 7, store access fault |
| MEPC | `0x4ff21e72`, `sw a4, 0(a5)` in `usj_fifo_write` |
| RA | `0x4ff21f2a`, the return into `usj_isr` |
| MTVAL | `0x500d2000`, `USB_SERIAL_JTAG.ep1` |
| a0 | 9, the byte index inside this call |
| a1 | 64, the chunk length |
| a4 | `0x39`, the byte being stored |

`MEPC` `0x4ff21e72` is `sw a4, 0(a5)`, which is `USB_SERIAL_JTAG.ep1.val = byte`. `MTVAL` is `0x500d2000`. `RA` is the return into `usj_isr`. The free bit had just read as 1. `a0` is 9 and `a1` is 64, so this was byte 9 of a full 64-byte chunk. The byte in `a4` is `0x39`. The chip is P4 v3.2, IDF 6.1, and it halted after about 3900 lines. Most earlier chunks stored through index 63, so the fault is intermittent.

## Why this store faults

The task and the ISR are both on core 0, and the ISR does not yield, so the task cannot set `WR_DONE` between that free-bit check and the store. The flush that matters is the one the task already did: it arms the IN packet, the host reads it, and the ISR is still writing. On this chip that store is a bus error. The free bit stays 1 across that window, so the check IDF 6.1 uses does not stop it.

A second capture of this same program also died with `a0` equal to 9, on a 59-byte chunk. That is only two samples. It is not a fixed 9-byte FIFO: this run stored index 63 many times before the panic.

## How to reproduce

Build with IDF 6.1 from this folder.

```bash
idf.py set-target esp32p4
idf.py -p <PORT> flash monitor
```

Use two serial ports at the same time:

- **USB Serial/JTAG** is the port `idf.py build flash monitor` uses. That terminal shows the build, the flash, and the monitor. The monitor prints the run, then it stops. It does not print the panic.
- **UART0** (GPIO 37 and GPIO 38) is the console. The boot log, the `[p4-usj]` progress lines, and the panic register dump are printed here. Open this port in a second terminal before starting the run.

`app_main` queues one log line at a time. After every byte it sets `WR_DONE`. The IN-empty ISR copies up to 64 queued bytes and stores each one with `USB_SERIAL_JTAG.ep1.val = byte` while `serial_in_ep_data_free` is 1, then sets `WR_DONE` once. It loops until the store faults. The panic handler prints the registers on UART0 and halts. Reset the board to run it again.

On this board the panic came after roughly 3900 lines.
